# Инструкции AI-агенту FinFast

## Перед началом работы

- Используй корневой `README.md` как вводный контекст о назначении, технологиях и запуске проекта; не копируй его описание в код/документацию без необходимости.
- Изучи соответствующий документ из `.ai/` **до изменения затронутой функциональной области**, затем проверь описанное поведение по текущему коду. `.ai/` описывает проверенное текущее состояние и отмечает известные несоответствия; это не спецификация будущего поведения.
- Найди реальные реализации и все затронутые слои. Не полагайся на старые пути/описания из сторонних заметок: здесь нет единого `backend/`; backend разделён на два сервиса под `services/`.

## Архитектура и краткая структура

- `client/` — Vue 3 + TypeScript PWA; UI в `src/views/` и `src/components/`, клиентское состояние/orchestration — `src/stores/`, REST wrappers — `src/services/api/`, local storage — `src/storage/`.
- `services/auth-service/` — Kotlin + Quarkus: аутентификация, управление пользователем, JWT/JWKS и outbox.
- `services/expense-service/` — Kotlin + Spring Boot: расходы, категории, data-change timestamps и их REST API.
- `docker/` — локальные Compose-конфигурации и Kafka; `.github/workflows/` — публикация frontend и backend.
- `.ai/` — техническая документация по архитектуре и функциональным областям; перечень ниже.

## Общие правила изменений

- Делай минимальные целевые изменения и сохраняй существующее разделение ответственности: UI → store → API/storage; backend controller/resource → service → repository.
- Не меняй поведение/API/схему на основании предположений. Проверь актуальные DTO, вызовы, миграции и consumers; фиксируй обнаруженные неоднозначности, не устраняя их автоматически в несвязанной задаче.
- Защищённые backend-операции определяют пользователя из security context/principal. Не доверяй клиентскому `userId` и не ослабляй ownership checks.
- Учитывай offline-first: не теряй локальные unsynced данные при сетевой ошибке, logout или обновлении данных; `navigator.onLine` не доказывает доступность сервера. Не смешивай данные anonymous и authenticated профилей без явного пользовательского действия.
- Сохраняй текущие контракты между frontend и backend; при их изменении обновляй оба конца и всех потребителей.
- Схемы сервисов управляются отдельными Flyway migrations. Добавляй новую migration в нужный сервис, не редактируй уже применённые; не полагайся только на ORM-аннотации.
- Не добавляй зависимости, если задача решается текущим стеком. Не включай секреты/credentials в код или документацию.
- Проверяй затронутую часть проекта. Для frontend предпочтителен `npm run type-check` из `client/`; для backend ориентируйся на Gradle wrapper и сборку именно изменённого сервиса.

## Документы `.ai/`

- `.ai/architecture.md` — компоненты, взаимодействия, стек, безопасность, offline-first и схема развертывания на высоком уровне.
- `.ai/authentication.md` — вход, токены, профиль, гостевой режим и удаление аккаунта.
- `.ai/expenses.md` — модель расходов, ownership, CRUD и ограничения persistence.
- `.ai/expense-sync.md` — локальные изменения расходов, API sync/batch и retry/reconciliation.
- `.ai/categories.md` — системные и пользовательские категории, состояния и backend-правила.
- `.ai/category-sync.md` — category queues, timestamp sync, retry и известные риски.
- `.ai/offline-first.md` — IndexedDB/localStorage, изоляция профилей, offline-поведение и logout.
- `.ai/import-export.md` — JSON/CSV форматы, validation, merge и ограничения.
- `.ai/deployment.md` — локальный Compose, PWA, CI/CD и production-конфигурация.

**Перед изменением конкретной функциональной области сначала прочитай соответствующий документ из `.ai/` и связанные с ним документы, затем сверь факты с исходным кодом.** Для сквозного изменения прочитай `architecture.md` и документы всех затронутых областей.
